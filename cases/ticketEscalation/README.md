# Передача на вторую линию

Worker-расширение для `ticket/view:common.before`. Кнопка открывает собственную
шторку передачи вопросов обращения специалисту. Менеджер выбирает вопросы,
сотрудника, новый статус, причину передачи, описывает выполненные действия
и ожидаемое решение. Перед применением видит назначения и текст комментария.

Применение последовательно вызывает `changeIssueResponsible`, `changeIssueStatus`
для выбранных вопросов и `createComment` для общей сводки. Другие вопросы не
изменяются. Это отдельные операции, а не транзакция: при отказе показывается
ошибка, а повтор продолжает незавершённые шаги текущего плана. Уже успешно
выполненные шаги не повторяются. При смене обращения план сбрасывается.
Предпросмотр устаревает при изменении выбранных вопросов до начала применения.

Сотрудники загружаются через `httpCall('/ticket-workflows/recipients')`.
Backend читает активных менеджеров из REST API CRM, включая все страницы ответа,
и возвращает только идентификатор и имя. Для работы нужны `CRM_API_HOST` и
`CRM_API_KEY` в `.env` с правом чтения пользователей. Искусственной подмены
сотрудников при ошибке API нет.

Контексты `ticket/view`, `ticket/view:settings` и `settings` инициализируются до
монтирования. Статусы берутся из настроек контекста; допустимость изменения
проверяет хост CRM. Для передачи нужны `editable` и `commentable`.
Учитываются загрузка, ошибки загрузки, `pending` и локальное выполнение.
Переводы доступны на русском, английском и испанском и следуют локали CRM.

## Запуск

```sh
yarn install
yarn build
yarn serve:extension
```

Метаданные находятся в `extensionrc.json`, delivery запись — в `cases.json`.
Скрипт доступен по `http://127.0.0.1:3000/extension/<uuid>/script`, стили — по тому
же пути с `/stylesheet`. Backend и delivery должны обслуживаться одним сервером.

В sandbox `0.9.33` используйте Widgets с fixture `ticket-basic` или `ticket-readonly`
и target `ticket/view:common.before`. Для чтения сотрудников настройте backend
HTTP base URL. Sandbox имитирует изменения и записывает их в snapshot, реальные
обращения он не меняет. Browser-тесты подменяют только ответ backend.

```sh
yarn test:browser tests/browser/ticketEscalation.browser.test.ts
yarn test:e2e tests/e2e/ticketEscalation.e2e.ts
```

Расширение не получает встроенные списки и не управляет их пагинацией.

## Устройство кода

- `WidgetApp.vue` — отображение и локализация интерфейса.
- `api.ts` — HTTP-запрос и проверка ответа backend расширения.
- `domain.ts` — подготовка текста и плана, проверка актуальности данных.
- `store/form.ts` — поля формы и доступность предпросмотра.
- `store/recipients.ts` — загрузка каталога и защита от устаревших ответов.
- `store/application.ts` — применение плана, учёт завершённых шагов и повтор.
- `store/escalation.ts` — сборка состояния сценария и его жизненный цикл.

Состояние создаётся для экземпляра виджета. Данные CRM читаются из контекстов;
локальная форма и план их не подменяют. HTTP-каталоги и применение изменений
имеют отдельные состояния загрузки и ошибок.
