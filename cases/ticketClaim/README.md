# Мастер оформления претензии

Worker-расширение для `ticket/edit:issues.after`. В точке встраивания отображается
компактная кнопка; форма мастера открывается в собственной шторке.

Сначала привяжите заказ в штатной форме CRM. В мастере выберите заказ и товары,
причину претензии (повреждение, неполная комплектация или другой товар), опишите
обстоятельства и желаемое решение. Подсказка поля обстоятельств зависит от причины.
Выберите существующий вопрос либо создание отдельного вопроса, затем тип и подтему
из справочников CRM. Значения справочников не зашиты в сценарий.

Предпросмотр показывает классификацию, выбранные товары и итоговое описание.
По кнопке «Применить» мастер:

- создаёт вопрос при необходимости и меняет его тип и подтему по локальному `key`;
- привязывает выбранные позиции через `addOrderItem`, пропуская уже привязанные;
- дополняет исходное описание структурированной претензией через публичный
  context accessor, ожидает ответ и перечитывает фактическое значение хоста.

Все изменения относятся к черновику, в том числе при `ticket.id === null`.
Сохранение, закрытие и валидация штатной формы остаются за CRM. Статус и
ответственный существующего вопроса сохраняются. Предпросмотр не меняет черновик;
изменение исходного описания или выбранного вопроса делает его устаревшим.

Операции не образуют транзакцию. При отказе показывается ошибка и остаётся
возможность продолжить незавершённые шаги текущего плана. Завершённые шаги не
повторяются. Для отмены уже внесённых изменений используйте штатную форму CRM.
В режиме создания учитывается `creatable`, при редактировании — `editable`;
загрузка, `saving`, `pending` и выполняющееся действие блокируют контролы.

Контекст `orderItems` содержит только уже привязанные позиции. Полный набор
товаров привязанных заказов мастер запрашивает через
`httpCall('/ticket-workflows/order-items', { orderIds })`. Backend читает заказы
по REST API, не меняя их. Нужны `CRM_API_HOST` и `CRM_API_KEY` с правом чтения
заказов. Один запрос принимает не более 20 заказов. Отдельного поиска заказов
и управления штатными списками в расширении нет.

## Запуск и проверки

```sh
yarn install
yarn build
yarn serve:extension
yarn test:browser tests/browser/ticketClaim.browser.test.ts
```

Метаданные находятся в `extensionrc.json`. Хост CRM должен предоставлять
`ticket/edit:issues.after`, контексты `ticket/edit`, `ticket/edit:settings`
и действия редактора. Backend и delivery обслуживаются одним сервером.

В sandbox `0.9.33` ещё нет editor fixture. Browser-тесты запускают настоящий
worker с отдельным хостом на публичных `sandbox/core`, схемах контекстов и RPC.
Этот хост моделирует операции черновика и не является реализацией хоста CRM.
См. `tests/browser/__fixtures__/ticketClaim.ts` и
`tests/browser/__utils__/ticketClaimRuntime.ts`.

Переводы доступны на русском, английском и испанском и следуют локали CRM.

## Устройство кода

- `WidgetApp.vue` — отображение и локализация интерфейса.
- `api.ts` — HTTP-запрос и проверка ответа backend расширения.
- `domain.ts` — подготовка текста и плана, проверка актуальности данных.
- `store/form.ts` — поля формы и доступность предпросмотра.
- `store/orderItems.ts` — загрузка каталога и защита от устаревших ответов.
- `store/application.ts` — применение плана, учёт завершённых шагов и повтор.
- `store/claim.ts` — сборка состояния сценария и его жизненный цикл.

Состояние создаётся для экземпляра виджета. Данные CRM читаются из контекстов;
локальная форма и план их не подменяют. HTTP-каталоги и применение изменений
имеют отдельные состояния загрузки и ошибок.
